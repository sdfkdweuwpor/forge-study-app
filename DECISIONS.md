# Decisions

One dated bullet per decision: what we decided, then why. Newest entries go at the bottom of their section.

## Hosting, deploy, tooling

- **2026-09-29 — Deploy to Netlify, not GitHub Pages.** The repo is private on a free GitHub plan, which rules out Pages. Netlify's free tier serves private repos. *Superseded on 2026-09-30 for the live app: see "Hosting: GitHub Pages" below. Netlify stays as a fallback.*
  - Vite uses `base: '/'`.
  - The site URL is one constant, `APP_ORIGIN = https://forge-study-app.netlify.app`, defined in `extension/src/shared/config.ts` and re-exported by `src/config.ts`.
- **2026-09-29 — Deploy mechanism.**
  - The coordinator deploys with the Netlify connector or CLI.
  - `.github/workflows/deploy.yml` also deploys with `npx netlify-cli deploy --prod --dir dist` on push to `main`, but only when the `NETLIFY_AUTH_TOKEN` and `NETLIFY_SITE_ID` repo secrets exist (the user adds them).
  - If the user connects the repo through Netlify's Git integration instead, delete `deploy.yml` to avoid double deploys.
  - Nothing is published from the branch until the coordinator deploys it or the user merges to `main`.
- **2026-09-29 — `netlify.toml` holds build, SPA rewrite and cache headers.**
  - Build: `npm run build`, publish `dist`, `NODE_VERSION=22`.
  - SPA rewrite: `/* /index.html 200`.
  - Cache: `Cache-Control: immutable` for `/assets/*`; `no-cache` for `/`, `/index.html`, `/sw.js` and `/manifest.webmanifest`.
  - A missing `/assets/*` file returns a real 404 (`/404.html`), via a rule placed above the SPA rewrite. Redirects only apply where no file exists (no `force`), so existing assets are served normally. Without it, a tab left open across a deploy gets `index.html` in place of a JavaScript chunk and fails with a MIME-type error.
- **2026-09-29 — Security headers come from one file, `security-headers.mjs`.** A 15-line Vite plugin writes it to `dist/_headers`, and the same object feeds `vite preview` headers. Playwright therefore runs under the production CSP, and the header list can't drift between two files.
  - The CSP is `default-src 'self'`.
  - `style-src` adds `'unsafe-inline'`: some libraries inject `<style>` elements or style attributes, and with `script-src 'self'` it cannot run script. React `style` props alone would not need it.
  - `font-src` adds `data:`, because Vite inlines small font subsets as data URIs.
  - `worker-src 'self'` only: workers are separate built files (`new Worker(new URL(...))`), never `blob:` or `?worker&inline`.
  - `img-src` adds `data:`, `blob:` and `https://icons.duckduckgo.com`.
  - `frame-ancestors 'none'`.
  - The theme bootstrap is an external `/theme-init.js`, so no inline scripts are needed.
- **2026-09-29 — Extension releases stay on GitHub Actions.** Releases work on private repos. Download links need the user to be logged in to GitHub, which is fine for a single user.
- **2026-09-29 — No Playwright MCP here, so verification uses a Playwright script.** `npm run shoot` runs `scripts/shoot.spec.ts` through the Playwright test runner, which gives TypeScript without `tsx`.
  - It serves the preview build, fixes the clock and seeds sample data.
  - It saves light/dark × 1440/375 PNGs to the git-ignored `screenshots/`. Agents review them with Read.
  - Curated shots for the README are committed under `docs/screenshots/` in Phase 13.
- **2026-09-29 — Pin `@playwright/test` to exactly `1.56.1`.** The environment ships chromium-1194 in `/opt/pw-browsers` (`PLAYWRIGHT_BROWSERS_PATH`) for that version. Never run `playwright install` locally; CI may install its own browser if e2e is ever added there.
- **2026-09-29 — CI (`ci.yml`) runs typecheck, lint, unit tests and build on every push and PR. e2e runs only in agent sessions.** This keeps the private repo within its 2,000 free Actions minutes.
- **2026-09-29 — Node scripts are plain `.mjs`; Playwright handles `.ts` specs.** This avoids adding `tsx` or `ts-node`.
- **2026-09-29 — PWA icons are rasterized from `favicon.svg` by `scripts/icons.mjs` using Playwright's Chromium.** This avoids `sharp` and `@vite-pwa/assets-generator`.
- **2026-09-29 — Lighthouse runs in Phase 13 via `npx lighthouse` with `CHROME_PATH` pointing to the bundled Chromium.** It is a one-off audit, so it isn't added as a dependency.
- **2026-09-29 — Subagents live in `.claude/agents/` and are invoked by type** (architect, designer, builder, reviewer, helper) with the `model:` from their frontmatter. Phase 0 ran through the general-purpose agent with an opus override because the session hadn't loaded the new types yet; they are loaded from Phase 1 on.
  - Parallel builders get disjoint file-ownership lists (PLAN §6).
  - Edits to shared files are serialized by the coordinator.
- **2026-09-30 — Hosting: GitHub Pages (Netlify stays as a fallback).** The live app is https://sdfkdweuwpor.github.io/forge-study-app/, deployed by `.github/workflows/pages.yml` on every push to `main` (and by hand).
  - **Why.** The repo is public now, so Pages is free for it. It deploys from GitHub itself with no tokens or secrets (Settings → Pages → Source: GitHub Actions is the only setup), and this container's network policy blocks Netlify, so a Netlify deploy could not be made or checked from here. https://forge-study-app.netlify.app keeps working from the root: same code, only the build's base path differs.
  - **Two builds of one codebase.** The default `base: '/'` (Netlify, `vite preview`, dev, e2e) and `vite build --base /forge-study-app/` (Pages). `import.meta.env.BASE_URL` is the only source of the base.
  - **Base-less inside, based at the boundary.** Every path in the app is base-less: routes, saved views, `navigate`, `navigateToUrl`, `isAppPath`, `usePathname`, `currentPath()`. Only `src/app/router/location.ts` converts, with the pure `withBase` / `stripBase` in `base.ts` (tested with both bases, at segment boundaries, and round-trip).
    - `getUrl()` and `currentPath()` strip the base; `pushUrl()` adds it; `href()` returns the based URL for a real `<a href>` (so a new-tab click works); `appPath()` is the base-less form for comparisons.
    - `Link` builds the base-less path once: `pushUrl` gets that, and only the anchor's `href` attribute gets `toHref(path)`, so it cannot double-prefix.
    - `pushUrl` also accepts a URL that already carries the base, and strips it before adding it back. Breadcrumb items, the `g` shortcuts and the Roadmap command hand `navigateToUrl` an `href()` result, and a future caller doing the same would otherwise break only on Pages (every e2e runs at the root base). It is unambiguous because no route is named `forge-study-app`.
  - **Action versions (checked 2026-09-30 with `git ls-remote`):** `configure-pages@v6`, `upload-pages-artifact@v5` and `deploy-pages@v5`, the current majors (Node 24). `upload-pages-artifact` v4+ leaves dotfiles out unless `include-hidden-files: true`, which the workflow sets so `.nojekyll` ships; an Actions-deployed site skips Jekyll anyway, so this is belt and braces.
    - Features ask `currentPath()`, never `window.location.pathname` (`setQuery` too). `boot.ts` keeps reading the full URL because it rewrites it as a whole. A root-absolute URL in TSX uses `BASE_URL` (the Welcome logo); Vite rewrites `index.html` and CSS itself.
  - **PWA under a base.** vite-plugin-pwa calls `integration.configureOptions` with the resolved Vite config, where `applyBase` in `vite.config.ts` prefixes the manifest's `id`, `start_url`, `scope`, icons and shortcuts and sets Workbox's `navigateFallback` and `navigateFallbackDenylist` (`/forge-study-app/assets/`, `.zip`, `/forge-study-app/404.html`). Checked on the real build: manifest and `sw.js` are scoped to `/forge-study-app/`, the page is controlled by the worker, and an offline deep link is answered from the precache. It is also the reason `--base` on the command line is enough.
  - **Shared origin.** `localStorage` and IndexedDB are per origin, not per path, so another Pages project of the same GitHub account would share storage with Forge (the `forge` database, `forge:` keys). Fine for one person's account; worth remembering if the account hosts other apps.
  - **404.html is the SPA fallback.** Pages serves `404.html` (status 404) for an unknown path, so `scripts/pages-postbuild.mjs` overwrites it with a copy of `index.html` and `/forge-study-app/tasks` loads Tasks. A cold deep link therefore logs one "Failed to load resource: 404" for the page itself; once the service worker is installed, its navigation fallback answers 200. A missing hashed chunk (a tab left open across a deploy) now gets the app shell with status 404 instead of Netlify's static page, which still fails the dynamic import, and `isChunkLoadError` handles it as before.
  - **Meta CSP, and its limits.** The script injects `<meta http-equiv="Content-Security-Policy">` into both HTML files, built at run time from `securityHeaders['Content-Security-Policy']`, so the two hosts cannot drift apart. It drops `frame-ancestors`, `report-uri` and `sandbox`, which a `<meta>` policy ignores, and sits right after the charset declaration because a meta policy only governs what is parsed after it. Limits: Pages sends no other header, so there is no `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` or `Permissions-Policy`, and the page can be framed. The worker script has no policy of its own there, so the `connect-src` note about favicons applies to Netlify only. Pages caches everything for 10 minutes; only `sw.js` is always revalidated by the browser's update check. Verified in Chromium: an injected inline script is refused and reported. The script runs after the worker's precache list was written; `index.html`'s revision there is that of the file before the meta tag, which changes exactly when the file does.
  - **`.nojekyll`** is written as belt and braces (an Actions deploy is not processed by Jekyll anyway). The Netlify `_headers` file is uploaded and does nothing.
  - **Extension.** `externally_connectable.matches` lists `https://sdfkdweuwpor.github.io/*` and `https://forge-study-app.netlify.app/*` (plus localhost). Chrome matches the whole `github.io` origin, which is every Pages project of the account, so `isAllowedOrigin` (the worker's own check) also requires the `/forge-study-app/` path on that origin. `extension/src/shared/config.ts` now has `APP_ORIGIN` (Pages, for origin checks), `APP_PATH`, `APP_URL` (origin + path, what the popup opens) and `FALLBACK_ORIGIN` (Netlify). The Blocker refuses to block either host or a parent of one (`github.io`, `netlify.app`).
  - **Open.** `src/features/sync/actions.ts` builds the magic-link redirect as `${window.location.origin}/settings/sync`, which has no base on Pages (it needs `href('settings', { section: 'sync' })`), and the Supabase Redirect URLs must list `https://sdfkdweuwpor.github.io/forge-study-app/settings/sync`. It belongs to the sync work and was left alone.

## Architecture

- **2026-09-29 — Routing uses a hand-written history router with typed routes, not react-router.** Netlify's SPA rewrite plus the PWA `navigateFallback` make clean paths safe, and they read better in breadcrumbs and shared links. *On GitHub Pages the same holds through `404.html`, and the base path is handled in `location.ts` only (see "Hosting: GitHub Pages").*
  - The router is about 150 lines. We only need a route table, params, an optional last segment, `Link`, `navigate`, `href`, `useRoute` and `useQuery`.
  - All URL access sits in `router/location.ts`. Switching to hash routing, for a host without rewrites, is a contained change.
  - `vite dev` and `vite preview` already fall back to `index.html`.
- **2026-09-29 — The complete route table is central, and features auto-register through `import.meta.glob('features/*/feature.ts')` manifests.** These provide routes, commands, shortcuts, search, slots, providers, domain handlers and `onAppStart`. Parallel builders then almost never edit the same file, links stay type-safe, and every route is lazy-loaded.
- **2026-09-29 — Named UI slots** (e.g. `course.panels`, `today.aside`, `settings.sections`). A later phase can add UI to another feature's page without editing it, which matters most for the 9 parallel extras in Phase 11.
- **2026-09-29 — Dexie liveQuery hooks are the store. Writes go only through `src/db/repos/*`. Contexts hold UI state only.** There is one source of truth, no cache invalidation, and no Redux or Zustand.
- **2026-09-29 — Domain events are emitted after commit (`src/db/events.ts`), and features subscribe to them.** This decouples derived data (streakDays, badges, daily-goal XP) from the core writes, and derived data can be rebuilt from history in `onAppStart`. The core XP award stays inside the task or session transaction, so undo is exact.
- **2026-09-29 — Layer rules are enforced by lint.** `logic/` is pure: no React, Dexie or DOM, and time is injected. `ui/` has no data access. Features import other features only through `index.ts`. That keeps logic testable and boundaries honest when many agents edit.
- **2026-09-29 — Use date-fns v4, not Temporal.** It is tree-shakeable and stable with no polyfill.
  - Calendar days are local `'YYYY-MM-DD'` strings; instants are epoch ms.
  - Never use `new Date('YYYY-MM-DD')`, because it parses as UTC.
  - Tests run with `TZ=America/New_York` to exercise DST.
- **2026-09-29 — TypeScript `strict` plus `noUncheckedIndexedAccess`.** The scheduler and stats index arrays heavily, and this catches off-by-one and undefined bugs at compile time.
- **2026-09-29 — IDs come from `crypto.randomUUID()`.** It is available in secure contexts (Netlify HTTPS, localhost) and needs no dependency. Natural keys are used where they're more robust: settings `'app'`, streakDays by day, badges by badge id, rituals `kind:day`, weekly reviews by week start, block events by extension uuid. These make idempotent upserts trivial.
- **2026-09-29 — Shortcut scopes: overlay scopes are blocking, and the controller alone decides what is live (Phase 3F).** The `modal`, `palette`, `fullscreen` and `drawer` scopes (`BLOCKING_SCOPES`; `pushScope(scope, { blocking })` overrides per push) hide everything beneath the topmost one. While one is on top, only its own shortcuts, scopes pushed above it (a scope opened inside a dialog) and `global` shortcuts with `allowInOverlays` may fire. That flag is separate from `allowInInputs`: `true` keeps a shortcut live under any overlay (`esc`, `mod+k`, `mod+enter` "quick add from anywhere"), and a list of scope ids keeps it live only under those (`mod+\` is `['drawer']`, so it still closes the tablet drawer but no longer collapses the sidebar behind a dialog). Everything else global (`q`, `g t`, `?`, `/`) goes quiet under an overlay.
  - Esc resolves the same way, with no special case: under an overlay the global `app.escape` (or the overlay's own `esc`) is the only Esc candidate, so the top overlay closes first; a page's `tasks.escape` gets Esc only once no overlay is open. `escapeActive` and the `useOpenOverlays().length === 0` guards in the tasks, view and Today hooks were removed. The Tasks page had the bug at 640-1023 px, where `escapeActive` was never passed. Two overlays that both bind `app.escape` (the drawer and `OverlayEscape`) still resolve by bind order, which matches open order because the only global that can open something under an overlay, `mod+\`, is limited to the drawer.
  - The Tasks page's `x`/`j` now also stop under the tablet drawer and the More sheet, which are not in `OverlayProvider` and were never covered by those guards. The drawer has its own `drawer` scope (it was `modal`, whose `mod+enter` "next step" in wizards must not run in a navigation drawer); `SCOPE_LABELS` names it.
  - `src/ui/Modal` cannot import the app, so it reports through `ModalPresenceContext` (`ui/Modal/ModalPresence.ts`): `Modal` calls the provided function while `open` and calls what it returns on close. `ShortcutProvider` provides one that pushes the blocking `modal` scope, so any Modal (the shortcut sheet, `/design`, the Phase 5 wizards) blocks the page with no per-caller code; the sheet's own scope push was dropped. Without a provider it does nothing. The palette and quick add still push `palette` and `modal` themselves. A Phase 4 full-screen focus view should push `fullscreen` and mark `p` (park a thought) `allowInOverlays`.
  - Menus and popovers report the same way, with kind `'menu'` (`FloatingLayer`, so `Dropdown` and `Popover`): `ShortcutProvider` pushes a blocking `menu` scope, the lightest overlay (no shortcuts of its own; `allowInOverlays: true` keys such as `mod+k` stay live). While one is open, a page key the menu does not use itself (`Mod+Backspace` trashes, `Alt+↓` reorders) no longer fires behind it, and neither does a key pressed while focus is still on the trigger. `DatePicker` is inline native inputs and needs nothing; inside a popover it is covered. Menus and popovers still take Esc first through `ui/Popover/layers`.
- **2026-09-30 — A page scope that mounts under an open drawer stays beneath it (`pinned`).** The More sheet's Esc failed about 1 run in 20 under load: the Today page is a lazy chunk, and when it arrived after the sheet was opened its `today` and `tasks` scopes were pushed *above* the `drawer` scope, so the deeper `tasks.escape` answered Esc ("clear the selection") instead of the global `app.escape` the sheet binds. A scope opened above an overlay is live by design (a scope opened inside a dialog belongs to the dialog), so the controller cannot tell such a page from a dialog's own scope; the drawer says so instead. `pushScope(scope, { pinned: true })` (`useShortcutScope(scope, active, { pinned })`) marks an overlay whose beneath-ness must not depend on mount order: a *non-blocking, non-pinned* scope pushed while a pinned one is on the stack is inserted beneath it, and blocking scopes (`modal`, `menu`, `palette`) still stack on top as before. Only `Drawer` pins (tablet drawer and mobile More sheet). `e2e/smoke.spec.ts` holds the Today chunk back with `page.route` to make the order certain, and the controller has unit tests for it.

## Data model

- **2026-09-29 — Schema v1 defines every table up front: the 21 in BRIEF §6 plus 5 extra.** The extras are `savedViews` (Notion-like saved views, §5.3), `rituals` (§5.11), `weeklyReviews` (§5.7), `templates` (§5.11) and `files` (PDF blobs kept apart, so resource lists and snapshots stay light). Later phases then almost never need a migration.
- **2026-09-29 — Migrations are append-only.** Never edit a released version string. Each new version gets its own `migrations/vN.ts`, a matching backup-file migrator, and a fake-indexeddb upgrade test. Old backups and snapshots must always restore.
- **2026-09-29 — Timestamps are stamped by Dexie `creating`/`updating` hooks, which only fill missing values.** Builders can't forget them, and restore and trash-restore keep the original timestamps.
- **2026-09-29 — Booleans and nullable fields are never used as index keys.** IndexedDB can't index booleans, `null` or `undefined`. Nullable dates simply drop out of the index; booleans are filtered in JS.
- **2026-09-29 — Trash moves the record, and its cascade, into a `trash` row with a JSON payload and a 30-day expiry, instead of a `deletedAt` flag.** No query ever has to remember to filter out deleted rows, and restore is one `bulkPut`.
- **2026-09-29 — `xpEvents` is append-only.**
  - Undo writes a negative event with the same `key`.
  - Awards are idempotent per key: skip if the key's net is > 0.
  - Lifetime XP is the sum of all events. Balance is lifetime minus unrefunded redemptions. Levels use lifetime XP.
  - This follows the brief: XP must never drift and must be auditable.
- **2026-09-29 — Levels: advancing from level n to n+1 costs `round(100·n^1.5)`, starting at level 1 with 0 XP.** This matches the brief's sidebar mock ("Level 7 … /1,800", and L7→8 = 1,852).
- **2026-09-29 — `streakDays` is a rebuildable daily aggregate cache. The streak freeze is computed, not stored.** The day's daily-goal target is snapshotted so later settings changes don't rewrite history. At most 1 freeze per week (by `weekStartsOn`). A frozen day keeps the streak but doesn't add to it.
- **2026-09-29 — Breaks are stored as `sessions` rows (`kind: 'break'`), and timers are always computed from timestamps.** The whole pomodoro cycle survives a refresh. Stats filter on `kind = 'focus'`.
- **2026-09-29 — Timer ticks run in a module Web Worker.** Hidden-tab main-thread timers are throttled to about once a minute, which would make the chime and notification late.
- **2026-09-29 — Anti-cheat:** a session counts if it reaches 80% of planned time. Stopwatch sessions have no plan, so they count at 10 minutes or more.
  - **2026-09-30 — It compares exact time, not whole minutes** (`elapsed × 5 ≥ planned × 4`: 9:59 of a 12-minute plan counts); XP stays whole minutes. A stopwatch is paid and counted for at most 4 hours, so one left running overnight cannot farm XP or fake a streak day. A planned session that is finished late ends at its planned end, not at "now".
  - **2026-09-30 — An early stop can be taken back.** A focus session that ended without counting (under 80%, or a stopwatch under 10 minutes) offers Undo in its toast (`reopenSession`): it runs again, and the wait is added to `pausedMs`. A counted session paid XP, so it is not undoable.
- **2026-09-30 — Focus with several tabs open.** Only one tab wins the settle at the end of a phase, so the "Done with this task?" queue is shared through `forge:focus:pending-end` (storage events): every visible tab asks it, answering in one closes it in the others, and a newer question waits behind an open one. One tab plays the ambient bed, elected with a Web Lock (`navigator.locks`); without Web Locks each tab plays as before. Audio is unlocked (the context created) only when sounds are on.
- **2026-09-29 — Priority is stored as a number (0 none to 4 urgent).** It sorts and compares for free. Labels are mapped in logic.
- **2026-09-29 — Subtasks are an embedded checklist array on the task, not separate task rows.** This matches Things/Notion checklists and keeps queries simple.
- **2026-09-29 — Notes (task, goal, course) are a small `Block[]` model with a hand-made block editor and slash menu.** The brief asks for `/todo /heading /divider /callout` only, which doesn't justify a rich-text dependency.
- **2026-09-29 — Device-specific UI prefs (sidebar width/collapsed, last tasks layout, a theme mirror for no-flash boot) live in `localStorage` behind try/catch. Everything else lives in the `settings` row.** Those prefs shouldn't sync between laptop and phone.
- **2026-09-29 — Sample data comes from `?seed=wgu|empty`, which lazy-imports `src/dev/seed.ts`, and only in builds compiled with `VITE_ENABLE_SEED=1`.** It is used for screenshots and e2e (realistic WGU data: C182, C172, C779, D278, C959, C867, C949).
  - `npm run dev` and both Playwright `webServer` commands set the flag. A deployed build never has it: the seed module is dropped from the bundle and `?seed=` is ignored (and stripped from the address). A crafted link therefore can't replace anyone's data, whether or not the database already holds any.
  - Never set `VITE_ENABLE_SEED` in Netlify's environment.
- **2026-09-29 — `TaskFilter`/`TaskSort` live in `src/db/types.ts`, not `logic/taskQuery`.** `SavedView` needs them, and `db` must not depend on `logic` for types; `logic/taskQuery` imports them from `@/db/types` instead.
- **2026-09-29 — Tables are typed `Table<T, ID, NewRow<T>>`.** `add`/`put` accept rows without `createdAt`/`updatedAt` because the hooks stamp them; reads always return full rows.
- **2026-09-29 — Stamping edge cases.** An explicit `updatedAt` in a change is kept (sync/import); a `put()` that omits `createdAt` keeps the stored one; an empty diff is not stamped. `ForgeDB(name, clock)` takes an injectable clock for tests.
- **2026-09-29 — New settings fields need no Dexie migration.** `ensureSettings()` (boot) backfills keys missing from `defaultSettingsData()` into the stored row; `getSettings()`/`useSettings()` apply the same backfill in memory and never write.
- **2026-09-29 — `useSettings()` is `undefined` only while loading; with no row it returns factory defaults.** "No row" means a fresh install, where defaults are the truth, and the shell can distinguish loading from loaded.
- **2026-09-29 — `updateSettings(patch)` merge rules:** plain objects merge key by key (including `tagColors`), arrays replace, `undefined` is ignored, `null` sets null, and `id`/timestamps can't be patched. Removing a tag color will need a dedicated repo function (Phase 3).
- **2026-09-29 — Event bus mechanics.** `emit()` inside a transaction queues on the *root* Dexie transaction's `complete` event and is dropped on abort; outside a transaction it dispatches on a microtask. Handlers run under `Dexie.ignoreTransaction` so they can open their own transactions. `settleDomainEvents()` awaits everything in flight (tests, boot). `DomainHandler` is a union over event types, built with `defineHandler()`.
- **2026-09-29 — `newId()` falls back to `crypto.getRandomValues` when `randomUUID` is missing.** `randomUUID` needs a secure context, and the dev server is sometimes opened over a LAN IP from a phone.
- **2026-09-29 — Task repo conventions (Phase 3A).** `createTask` appends with `order = Date.now()`, so adding never scans the table; reordering uses fractional `orderBetween(above, below)` and renumbers the whole list only when two neighbours are closer than 1e-3. `updateTask` cannot change `status`: `setTaskStatus` routes done through `completeTask` and back through `uncompleteTask`, so XP and recurrence cannot drift. Editing the date or time of a `source: 'schedule'` task pins it (`schedulePinned`), as the scheduler decision requires.
- **2026-09-29 — Completing a recurring task creates the next instance in the same transaction, on the first occurrence after both its due date and today.** A daily task finished three days late is next due tomorrow, not in the past, and an every-other-week series keeps its phase. The new row shares `seriesId` and keeps the checklist unchecked. Undo removes exactly that row; reopening a task by hand removes the generated instance only while nobody has touched it.
- **2026-09-29 — An XP reversal is filed under the day of the award it cancels, with `at` set to when the undo happened.** That day's total nets out, and "XP today" never shows a negative number because you undid yesterday's task. `awardXp` skips a key whose net is positive; `reverseXp` appends the negative of the standing net; `getXpSummary` is derived from the log and redemptions on every read.
- **2026-09-29 — Trash is generic over tables.** `moveToTrash(table, id)` gathers a task (its checklist is embedded), a course (units, tasks, assessments, flashcards, resources and their files) or a goal (all of that plus its own tasks) into one `TrashItem` in one transaction. Restore is `bulkPut` per table, so ids and timestamps survive, and it emits `task.changed` / `goal.changed` for what came back. XP events are never trashed. `purgeExpired(now)` exists but is not wired to `onAppStart`; that belongs to Phase 11c.
- **2026-09-29 — Undo closures use the time they run, not the time of the action.** The `now` option on repo functions is for tests only; a reversal recorded by an undo an hour later says so.

## Scheduler

- **2026-09-29 — Courses are scheduled sequentially from one queue, in topological prerequisite order.** Priority is: active course first, then `order`, then code. This matches how WGU students take courses (one at a time) and makes prerequisites automatic. A cycle is reported and ordering falls back to `order`, so the preview still renders.
- **2026-09-29 — Chunk rules.**
  - Chunks are 25–90 min, in 5-min steps, and a day never goes over its capacity.
  - Tiny tails are avoided by leaving one 25-min final chunk. When that isn't possible, a short final chunk is accepted.
  - If a user's whole week is under 25 min/day, the minimum chunk drops to their largest daily capacity (`minEff`), so a schedule can't stall.
- **2026-09-29 — The schedule is materialized as real `tasks` (`source: 'schedule'`) and reconciled by `diffSchedule` on a stable `scheduleKey = unitId:seq`.** Goal work then appears in Today, Board, Calendar and .ics with no special cases, and user notes on chunks survive rebalances.
- **2026-09-29 — Manual date edits pin a scheduled task, and the rebalancer leaves pinned tasks alone.** Pins expire once their date has passed. This respects the user's choices without letting stale pins block progress.
- **2026-09-29 — Rebalance runs automatically at the first app open each day, and on edits, early completion, skip and catch-up.** Skipped tasks reserve their minutes for today so they move forward.
- **2026-09-29 — Catch-up is found by linear search in 5-min steps.** "Add X min/day" is the smallest X that is actually verified by re-running the scheduler. "Required h/day" is a verified uniform capacity. Both are correct even where the chunking makes feasibility non-monotonic.
- **2026-09-29 — Availability is per goal, and multiple goals don't share one capacity pool.** This is a documented limitation that keeps the algorithm simple. Global days off apply to all goals.
- **2026-09-29 — The slip ("+9 days") is measured against `targetDate`, or against the accepted plan's `baselineEnd` when there's no target.** The brief shows slip relative to a promise.
- **2026-09-29 — Scheduler as built (Phase 5A): the chunk rule.** `take = min(90, unit remainder, day left)`; if that leaves a tail under minEff and the unit is at least 2 × minEff, take `remainder − minEff` so the last piece is exactly minEff (100 min on a 120-min day is 75 + 25); a day with less than minEff left only takes a unit's whole remainder. So every chunk is 25–90 min (minEff–90) except a unit's final chunk. Greedy, as-soon-as-possible filling: each day is filled to its capacity from the head of the queue, which is what "push work forward, never above the daily max" means, and makes a missed day shift the plan by exactly one study day.
- **2026-09-29 — The scheduler walks integer day numbers, not `Date`s.** Days are counted from 1970-01-01 with Hinnant's civil-date arithmetic (`capacity.ts`), so there is no clock time and DST cannot duplicate or drop a day; a test checks them against date-fns across both 2026–27 DST changes and a leap day. It is also fast enough for catch-up to re-walk dozens of times: a 12-course year plans in about 1–4 ms and plan + catch-up in under 5 ms (the test budget is 50 ms).
- **2026-09-29 — Keys reuse free numbers.** A new chunk takes the smallest chunk number not held by a done or pinned chunk of its unit (`usedSeqs`), not simply "after the last done one". Finishing chunk 3 before chunk 1 then leaves the open tasks' keys (1, 2, 4) unchanged instead of renumbering the whole unit. The title's "(2/4)" is the key's number over done + pinned + planned chunks.
- **2026-09-29 — Pinned work is its own input (`ScheduleInput.pinned`), not just reserved minutes.** It still consumes its day's capacity, but it also counts toward `projectedEnd` and the course window, so dragging the last chunk two weeks out moves "Now projected" too. A pin lapses when its day has passed, when the task is skipped today (skip beats pin), or when its unit or course is done. A pinned task with no date is left alone and uses no capacity.
- **2026-09-29 — Skipping defers, it does not just reserve.** Skipped minutes reserve today's capacity (PLAN §4.3) and are also marked `deferredMinutes` on their unit, which may not land on today; on today only the rest of the unit is available (in pieces of at least minEff) and the walk looks past it to later units. Without that, a skipped chunk at the head of the queue came straight back to today. The diff never matches a task skipped today to a chunk dated today: it takes a later chunk of its unit, swapping keys with an unskipped task if needed, so the skipped task moves and the rest of today stays as it was. Idempotent on the next run.
- **2026-09-29 — Today's finished chunks reserve their minutes today.** Finishing a chunk does not pull tomorrow's work into today; working ahead on tomorrow's chunk pushes one of today's to tomorrow. Only `source: 'schedule'` tasks count (flashcard reviews and the user's own goal tasks do not use goal capacity yet).
- **2026-09-29 — Dropped chunks with user content go to the trash, detached.** An unneeded chunk (its unit was finished or shortened) is deleted outright only when untouched; one with notes, a checklist, tags, a priority, or in progress is turned into a plain task (`source: 'user'`, no key) and moved to the trash, so it can be restored and the rebalancer will not delete it again. Unmatched tasks are first re-keyed to a free chunk of the same unit, which keeps notes when a unit is re-chunked.
- **2026-09-29 — `rebalanceGoal` writes only what changed.** Tasks are updated field by field, courses and the goal only when their dates or projection differ (ignoring `computedAt`), and events fire only then; a second run the same day writes and emits nothing. So a `goal.changed` → rebalance handler settles after one extra run. It plans any goal it is given; the daily run decides which statuses to include. `baselineEnd` is set on `reason: 'wizard'` or when the goal has none.
- **2026-09-29 — Catch-up aims at the same date the slip uses (`targetDate ?? baselineEnd`).** PLAN §4.2 only suggested catch-up with a target; without one the goal page would show "+9 days" with no way to act. `projectedEnd` is `null` for `NO_AVAILABILITY` and `HORIZON_EXCEEDED` (a partial last date would look like a real end).
- **2026-09-29 — Units vs course hours.** When every unit has an estimate, their sum is the course's work (the WGU sample's D278 units add up to 34 h against 45 h on the course); units without one share what is left of the course hours in 5-min steps, and get 0 when nothing is left. A course without units is one synthetic unit (id = course id, "Study session", `unitId: null` on its tasks). Cycle members are released one at a time from the "source" component, so courses that merely depend on a cycle still come after it.

## Planner (Goal Breakdown Planner, slot-level)

- **2026-09-30 — The slot planner is a new entry point (`planStudy`) beside the day-level scheduler.** `buildSchedule`, `planGoal` and `diffSchedule` are unchanged and keep serving v1 goals until 5G switches `rebalanceGoal` over. All the new logic is pure and lives in `src/logic/scheduler/`, and parsing in `src/logic/planParse/`. There are no schema changes before 5G, because three builders are editing the repos in parallel.
- **2026-09-30 — Availability v2 is windows, not minutes.** It is per-weekday `HH:mm` windows (several a day, `24:00` allowed as an end; an overnight shift is two windows), a session length, blackout ranges, and an optional shift cycle (anchor + N days) that replaces the weekdays. Blackouts still apply over a shift cycle. The v1 `minutesByWeekday` becomes one window per study weekday starting at `settings.scheduling.defaultStudyStart` (the logic default is 18:00). It moves earlier when it would run past midnight.
- **2026-09-30 — DST: the skipped hour (spring) and the repeated hour (autumn) are taken out of that day's windows.** Wall-clock length then always equals real length, and no session straddles a change. The only loss is study planned 1–3 a.m. on two nights a year. The DST span is found with `new Date(y, m, d, h)` in the runtime zone, the same local-time assumption `logic/dates.ts` makes.
- **2026-09-30 — Effort: hours, else CUs × a user multiplier (default 15 h/CU: a 3-CU course ≈ 45 h), × a self-rating factor (know 0.5, somewhat 0.8, new 1.0).** The factors are rough "how much is left to learn" shares; the multiplier is the user's to tune. v2 keeps `baseEstimateMinutes` so re-rating recomputes.
- **2026-09-30 — The buffer is reserved capacity at the tail, not inflated effort.** 12 % of the planned work (10–15 % in the UI) is walked as free time after the last item at the plan's pace, giving `bufferedEnd`, and the plan fits when that is on or before the target. Inflating the sessions instead would make an on-track student do 12 % extra work. Tail slack is also what missed work rolls into.
- **2026-09-30 — Study is split as it is placed, not pre-split.** The planner first sized every session to the target length up front. With 50-min sessions that wasted up to a third of a 90-min window, and the WGU year at full speed ended in February 2028 instead of November 2027. Now a piece is the first of an even split when it fits, otherwise a piece of at least 25 min that fills the window without leaving under 25. A unit that fits in one session is never broken up. `splitMinutes` stays as the even split (readiness reviews, first-piece sizing).
- **2026-09-30 — A 10-min break between planned sessions, when there is room; back to back when not.** A hard break made a 2-hour window hold only one 60-min session.
- **2026-09-30 — Pace: ASAP without a target; with one, the smallest verified pace.** The pace is a token bucket (each study day adds `pace`, capped at pace + the longest item), so the average is exactly `pace` even when sessions are longer than it, and a day gets at most one extra session after days that could not use theirs. The pace is found by binary search, and every candidate is a real run. The first cap, max(pace, longest item), threw tokens away and under-delivered the pace. `planning.asap = true` with a target means full speed with the target only checked.
- **2026-09-30 — Assessments.** A dated one is fixed: a booked time blocks its slot, and without one it is a day marker, because the student books exam times. Its practice test and reviews are placed first, on study days before it: exam −7/−3/−1 plus practice −2; quiz −1; project −2. Offsets are scaled by gap/(max+1) when fewer study days are left and deduplicated against the practice day. An undated one is placed on the first study day after its course's last item, and gets that day's first free slot. Its extras are due at the point of the course's work that is about k study days from the end, so no second pass is needed. Study on or after a dated assessment of its course (`ASSESSMENT_TOO_EARLY`) makes the plan not fit.
- **2026-09-30 — Weekly milestones are derived markers** (`milestone:${weekStart}`), one per week with work or an assessment. They are dated on that week's last day with work and say which units finish that week ("Week of Oct 5 — finish C182 Units 3–4"); a week that finishes none says "continue …". Unit numbers are positions in the course, and courses are listed in plan order. Month names are fixed English, so titles do not depend on the locale.
- **2026-09-30 — Feasibility options are all verified by re-running the planner.** The searches use full-speed runs, which fit exactly when some pace fits. Add-time is a binary search over +5-min steps up to +4 h, applied as a later end of each day's last window (then an earlier start). Move-date is the full-speed `bufferedEnd`, checked. Cut-scope is greedy in candidate order (optional, then "know", "somewhat", then latest in the plan), then pruned; it is never "cut everything". The shortfall comes from the run itself: work after the target, the part of the buffer the target cuts off, and study after a dated assessment. A raw capacity estimate ignored breaks and said "5 min short" when 170 min were missing.
- **2026-09-30 — Roll-forward is move-only and push-only.** Keys, lengths and order are kept, and an item never moves earlier than its slot. Missed items (slot before today, or before `now` when given) take the next open slots, and later ones move only as far as needed. A paced plan keeps its pace with the planner's bucket, started full, so an on-track plan reflows to exactly itself and a missed session is absorbed in the headroom first. A missed review or practice test goes to the nearest free slot before its assessment, or is dropped (reported). A pin lapses when its day passes. Re-splitting or re-pacing is a proposal, never automatic.
- **2026-09-30 — Behind thresholds.** *Far behind* means any of:
  - the end slips more than 7 days past the baseline end (else past the previous end);
  - missed work is more than 15 % of the remaining work;
  - the end passes the target;
  - study lands on or after a dated assessment.

  Otherwise a plan with misses is *slightly behind*, and its roll-forward may be applied silently (`autoApply`). Far behind returns proposals (keep going, extend date, add time, cut scope, spread) and applies nothing. In ASAP mode "extend the date" is accepting the new end (it resets the baseline).
- **2026-09-30 — "Life happened" (`replanWeek`) is always a proposal.** It clears the rest of the week by default (capacity factor 0), or only the `blockedDays` given, or keeps a share of each window (`capacityFactor`). The week's work moves later, push-only; pinned items and reviews on cleared days move too; a booked exam stays.
- **2026-09-30 — Everyday auto-slot: earliest due first, then shortest, each at its earliest open slot that ends before it is due.** Tasks are never split; a task with no estimate counts as 25 min; the results are `noRoom` or `pastDue` otherwise. Earliest-deadline-first is the classic order that meets the most deadlines on one timeline. Opting a task in (`autoSlot`) is the confirmation, so applying its slot needs no further prompt.
- **2026-09-30 — `planParse` is line heuristics, not a grammar.** Noise lines are ignored. Course lines start with a code (`C182`, `CS 101`) and carry CUs, credits, OA/PA and hours. Headers (week, module, chapter, unit, lesson, …) are units, and whatever sits under one is its details. Assessments are exam words anywhere, or project words at the start when dated, due, or top-level; review, prep and practice lines are study. A single line, or text with no structure, is a typed goal (`needsBreakdown`, and its deadline read from "by June 2027" or "in 6 months"). Numeric dates are month first. A date without a year takes the year that puts it at most 60 days back. It outputs the shared `PlanDraft` from `planImport/draft.ts` (a type-only import) and keeps `needsBreakdown` and `confidence` on the result, so the import builder's type is not changed.
- **2026-09-30 — v2 task dates: `doDate` = when to do it, `dueDate` = a hard deadline only.** The migration moves every v1 `dueDate/dueTime` to `doDate/doTime` and clears the due fields. The single v1 date always meant "the day to do it" (quick add, the scheduler, Today), and turning every task into a deadline would light up false "overdue" badges. "Rolled over" reads `doDate`; "overdue" reads `dueDate`. Planner items get a `dueDate` only when an assessment bounds them.
- **2026-09-30 — Planned assessments get their own table (`plannedAssessments`), separate from `assessments` (attempt logs with scores).** One is a plan and the other a history, and readiness will join the two.
- **2026-09-30 — Performance.** A 12-course year with reviews, milestones and slots plans in about 10–16 ms paced (about 8 runs) and 3–5 ms ASAP; the test budget is 50 ms. Windows per day are memoized across the pace search, and each run's free time is a lazy per-day map.
- **2026-09-30 — Schema v2 applied (5G): one pure row mapping for the upgrade and for backups.** `logic/schemaV2.ts` maps each row idempotently; `db/migrations/v2.ts` runs it in the Dexie upgrade and `logic/backup.ts` (`migrateBackupV1toV2`) runs it on backup tables, so an old backup imports exactly like an upgraded database (a test checks they are equal). Trash payloads are mapped too, because restoring a v1 row after the upgrade would otherwise bring back an old-shaped row. The WGU planned assessments get ids derived from the course (`${courseId}:oa|pa`), so re-running cannot duplicate them, and a finished course's are created done.
- **2026-09-30 — A migration does not stamp `updatedAt`.** The timestamp hook skips rows changed inside the native `versionchange` transaction (Dexie wraps upgraders in a `'readwrite'` transaction, so the hook checks `tx.idbtrans.mode`). Otherwise every row would look freshly edited after the upgrade, which would matter for last-write-wins sync.
- **2026-09-30 — A task with a deadline but no do date is planned for its deadline (`planDay = doDate ?? dueDate`).** Today, Upcoming, the board and the calendar read `planDay`, so "Pay the phone bill, due Fri" shows up on Friday even though nobody picked a day (and auto-slotting, when opted in, picks an earlier one). The deadline itself never moves a task between lists, is never red, and is amber only on its day. A date filter keeps its stored name (`due`) so saved views and links still work; it now means the planned day.
- **2026-09-30 — No guilt: "Rolled over" became "Carried over", and nothing says "overdue".** Each carried-over row says the day it came from ("from Tue"), the group header and the date chip are neutral (no amber), the date group in lists is "Carried over", and the calendar's accessible name says "carried over". "Move all to today" stays (`shift+t`, and the palette command now named "Move carried-over tasks to today", which still matches "rolled over").
- **2026-09-30 — Quick add: a plain date or time is when to do it; `due`, `by` and `deadline` make a deadline.** "pay bill Fri" is planned for Friday, "pay bill due Fri" is due Friday (and planned for its deadline until moved). A time right after a deadline date, or after `by`/`due`, is the deadline's time; with no deadline date it falls on the do date, else today. `by` now always means a deadline ("Submit essay by 5pm"), which reads as intended. The result has `when` and `deadline` instead of `due`, and deadline chips are their own token kind.
- **2026-09-30 — `rebalanceGoal` runs the slot planner; the day-level scheduler stays for its tests only.** Plan items become tasks by key with their kind, do date and time, duration and (for reviews, practice tests and assessments) the assessment date as deadline. Reserving the same length at the end of today's windows is deterministic across runs, gives today one session less, and moves the skipped task to a later session of its unit (the diff's skip passes). Sessions finished today keep their own slot blocked, so finishing early does not pull more work in.
- **2026-09-30 — Everyday tasks with a do time, and other goals' sessions, are blocked slots for a goal's plan.** One person cannot be in two places; goals are still planned one at a time, so the first one planned gets the slot (the next run of the other plans around it).
- **2026-09-30 — A planned assessment counts as done when its item is checked off or its course is marked done.** Checking off "C779 · Objective assessment" stops its reviews from being generated; marking a course complete (WGU: passing it) needs no exam.
- **2026-09-30 — Proposals are rows, applied only on confirmation, and go stale.** `rollForwardGoal` writes the far-behind choices as `planProposals` (pending) and changes nothing else; a later run marks older pending ones stale. `applyProposal` refuses (marks stale) a proposal computed on another day or from a different open plan (`baseRevision` = a fingerprint of the open items). Move-only proposals (roll forward, "life happened") carry their items and are written as they are; the others change the goal (target date, windows, pace) or trash the cut units and then re-plan. Undo restores the goal, units, plan tasks and proposal statuses from a snapshot. `apply` is checked by a hand-written guard, not Zod, because the repo is in the first chunk. The daily run is `runDailyPlanning`, gated by `settings.scheduling.lastDailyRunDay` and skipping goals already planned today; the goals feature starts it from `onAppStart` with a dynamic import.
- **2026-09-30 — Legacy minutes become windows as they are, breaks included.** "2 h on Mondays" is a 09:00–11:00 window (from `defaultStudyStart`), and the planner's 10-minute breaks between 50-minute sessions come out of it, so a window holds a little less study than its length. That is the honest reading of "I have two hours", but it made the WGU template and sample miss their terms, so their windows were widened (template Mon–Fri 2.5 h, Sat 4 h; sample Sun/Fri 1.5 h, Mon–Thu 2 h, Sat 3 h). Planning windows and weekday minutes are kept in step by the repo (`logic/goalPlanning.ts`): new minutes rebuild only the changed days' windows from where each started; new windows rewrite the minutes; `asap` is kept.

The `AutoSlotSuggestions` card is exported from `@/features/tasks`; shortcut `shift+a` accepts all, and the palette has "Accept suggested times". Opting a task in is the toggle on its page (quick add has no token for it).

Drag the bottom edge (snaps to 15 min) or press Alt+Shift+↑/↓; resizing a plan session pins it, like moving it. Only plan sessions and anything filed under a goal or course take a goal colour; everyday tasks stay neutral. Deadlines are thin markers under the day's date (amber only on the day itself), and the all-day strip is labelled "untimed".

The draft is validated with Zod and kept in localStorage (`forge:planner:draft`), so a refresh loses nothing. The preview runs `planGoalSlots` over the rows the draft would save (`plannerRows`) and `checkFeasibility` over its input, so what the preview says is what `rebalanceGoal` builds; each of the three ways out of an infeasible plan is verified by that same run.

Claude's plan lands on the Effort step, then Review; nothing is scheduled before Confirm. Loading anything over an existing outline shows an Undo toast.

The reducer and `withoutUnitKeys` write the shares down first (`freezeShares`), then remove. A course whose every unit is cut goes too.

## Design system

- **2026-09-29 — Theme tokens work on any element (Phase 2A).** The selectors are `:root, [data-theme='light']`, `[data-theme='dark']`, and a `prefers-color-scheme: dark` block for `:root:not([data-theme])` / `[data-theme='system']`. That block repeats the dark values, and `contrast.test.ts` fails if the two drift. This lets `/design` nest a dark column inside a light page.
  - Accent presets set raw `--_accent-*-l/-d` values on `[data-accent]`. Each theme block maps them to the public `--accent*` tokens, so the mapping re-resolves inside a nested theme. To preview an accent on a sub-tree, set both `data-accent` and `data-theme` on it.
  - Colour tokens are literal hex or `rgba()` only, so the test can parse and composite them. Shorthands that reference theme colours (such as `--focus-ring`) are declared on `:root, [data-theme]` so they resolve per theme.
- **2026-09-29 — Colour naming and contrast tiers (WCAG AA, enforced by `src/styles/contrast.test.ts`).** The surfaces are `--bg`, `--bg-sidebar` and `--bg-elevated`, each plain, with `--bg-hover` and with `--bg-active`.
  - `--text` and `--text-muted` reach at least 4.5:1 on every surface. Use them for all small text, including placeholders and keyboard hints.
  - `--text-faint` reaches at least 3:1. Use it only for large text (≥ 24 px, or ≥ 18.66 px at weight 700), icons, disabled text and decorative separators.
  - `--{accent,success,warning,danger,xp}` are for fills, icons, bars and rings, at least 3:1.
  - `--{…}-text` is coloured text, at least 4.5:1 on the surfaces and on its own `--{…}-soft` tint.
  - `--accent-contrast` is text on an `--accent` or `--accent-hover` fill, at least 4.5:1.
  - `--bg-inverse` with `--text-inverse` and `--text-inverse-muted` is for tooltips and toasts.
  - `--border` and `--border-strong` are decorative hairlines, not held to 3:1. Controls are identified by their label or text and by the focus ring.

The JSON is written one table at a time with the main thread handed back between tables (`logic/snapshotJson.serializeInChunks`, byte-identical to `JSON.stringify`), the read is one short read-only transaction and the only write is one small row in `snapshots`. Measured with CDP thread time for the whole click (read, write, gzip, toast, list): 80–95 ms on the WGU sample, 120–260 ms on `wgu-year` (1.8 MB of JSON); `e2e/snapshots.spec.ts` asserts under 300 ms.
- **2026-09-30 — Daily snapshot rules.** At app start, when the newest `daily` snapshot is from an earlier local day (`dailyDue`; a clock set back does not repeat it) **and the app holds data** (`hasUserData`: an empty app, a fresh install or a reset, writes nothing), one is written. Retention (`snapshotsToPrune`, run after every write and at app start): the newest **7 automatic** and the newest **5 of each other kind** (manual, pre-import, pre-reset, pre-restore), which replaces PLAN §3.5's "3 of the others" and also trims the copies import and reset write without pruning. A kind this build does not know (a newer build's) is kept whole, never pruned. Import and reset behave as decided in 10B; only their daily-snapshot neighbour is new, so `e2e/settings.spec.ts` now looks at the non-automatic rows.
- **2026-09-30 — Restore is one transaction, keeps the files, and can be undone.** `restoreSnapshot` reads and validates the snapshot with the import's own rules (a bad or newer one stops before anything is written), writes a `pre-restore` snapshot of the data as it is (if that fails, nothing changes), then clears and refills every backup table except `files` in ONE transaction (`planRestore` migrates an older snapshot on the way in) and completes the settings row. **The `files` table is left alone**, because snapshots hold no bytes: PDFs still on the device stay attached, and one deleted since shows "file missing". The dialog, the section and the toast say PDFs, the Trash's included, are left as they are. The section confirms in a dialog (what is replaced, with what, and that a "Before restore" copy is taken), reloads, and the next page shows "Snapshot restored · N items" with **Undo**, which restores the pre-restore snapshot the same way. - **2026-09-30 — Links are http or https and nothing else, checked twice.** `parseWebUrl` (on add and edit, and again in the repo) accepts `http:` and `https:`, adds `https://` when the scheme is left off (`developer.mozilla.org/docs`), and calls every other scheme `blocked` whatever its case or spacing (`javascript:`, `data:`, `file:`, `ftp:`, `mailto:`, `blob:`); whitespace or control characters inside the text make it `invalid`, which also closes the `java\tscript:` trick. ## Cloud sync (Phase 12A)

- **2026-09-30 — Plain `fetch` against GoTrue and PostgREST, not `@supabase/supabase-js`.** Measured with esbuild (minified, gzip -9): `createClient` from supabase-js 2.117.2 is 222 KB / 58 KB gzip, auth-js + postgrest-js alone 121 KB / 30 KB. A lazy import would keep it out of the entry chunk, but the PWA precaches every JS chunk, so every install would download it with sync off. - **2026-09-30 — The person brings their own Supabase project; its URL and anon (publishable) key live in the device-local `syncState` table.** Nothing is hard-coded and sync is off with no row. The anon key is public by design (RLS protects the data), so this is not "storing a secret" in the brief's sense. Validation refuses a service-role JWT and any `sb_secret_…` key with a plain explanation, and a JWT for another project's ref. The session (access and refresh token) is the person's own login, kept only in `syncState`: never synced, never in a backup, snapshot, crash export or error report. A new-format `sb_publishable_…` key is sent only as `apikey`, never as a bearer (it is not a JWT; supabase-js does the same).
- **2026-09-30 — CSP `connect-src` gains `https://*.supabase.co`, a static wildcard.** A CSP is a response header fixed at build time; it cannot follow a URL typed into Settings later. The wildcard covers every hosted project and nothing else (no `wss:`, realtime is unused). Custom domains and self-hosted Supabase therefore cannot sync, and the URL check says so before anything is saved. Playwright mocks must use a `https://<20 chars>.supabase.co` origin, because the CSP is checked before `page.route` sees a request.
- **2026-09-30 — One generic server table, `forge_rows(user_id, tbl, id, updated_at, device_id, deleted, schema_version, data jsonb, seq, modified_at)`, not a table per Dexie table.** 26 synced tables would mean 26 tables, 104 policies and a migration in the person's project with every Forge schema change; jsonb rows carry their `schema_version` and clients migrate on read, so the server never migrates. We lose server-side queries on fields, which nothing needs.
- **2026-09-30 — Last-write-wins, the clock cap and the cursor are enforced in the database (a `before insert or update` trigger), not only in the client.** An older write returns `null` from the trigger (skipped), ties go to the larger device id, an equal stamp from the same device is accepted (a retried push is harmless), and a stamp more than 5 minutes past server time is capped there. Verified on PostgreSQL 16 with a Supabase shim, including RLS isolation between accounts and `anon` being denied.
- **2026-09-30 — The pull cursor is a server `seq` drawn under a per-account advisory lock, not `updated_at` or `modified_at`.** Client stamps cannot order other devices' writes, and server `now()` is the transaction start, so a transaction that starts earlier can commit later and be skipped by a timestamp cursor; rows of one push also share `modified_at`. Taking `pg_advisory_xact_lock(hash(user_id))` in the trigger before `nextval` makes seq order equal commit order per account (checked: a second concurrent push waits and gets the larger seq, a reader in between sees neither). The `BEFORE INSERT` trigger fires before the conflict check, so the lock always comes before any row lock: opposite-order pushes did not deadlock. Clients only ever upsert.
- **2026-09-30 — The LWW stamp is the time of the write on the writing device, from a hybrid clock, not the row's `updatedAt`.** Trash restore, snapshot restore and import keep a row's original `updatedAt` on purpose, so an `updatedAt` rule would let the older tombstone of a restored item win and delete it again everywhere. The stamp is `max(Date.now(), last + 1, maxSeenRemote + 1)`: strictly increasing per tab, and an edit made after seeing another device's change always beats it, whatever the clocks say. For ordinary edits it is the same moment as `updatedAt`, so the brief's rule holds; `updatedAt` is still the stamp of a device's first push (a phone's week-old default must not beat the laptop's newer edit).
- **2026-09-30 — Changes are tracked by an outbox written by a Dexie DBCore middleware, not by scanning `updatedAt > lastPushedAt`.** A scan cannot see deletes, misses restored rows (old `updatedAt`), and would need an `updatedAt` index on every table plus full scans. The middleware (level 10, above Dexie's hooks) widens every read-write transaction that touches a synced table to include `syncOutbox` and writes one `{tbl, id, at}` entry per record it changes, in the same transaction; push reads the row at push time (gone → tombstone). It sees every path: `update`, `modify`, `bulkPut`, `delete`, `where().delete()`, `clear()` (as `deleteRange`, whose keys it queries first), trash moves, restores and imports. Prototyped on dexie 4.4.6 with fake-indexeddb: the `trans` a middleware receives is the transaction's `idbtrans`, so a `WeakSet` marks the sync's own apply transactions as untracked (the timestamp hook sees the same marker and must not stamp them); nested transactions are tracked once; upgrades are never tracked; outbox writes pass through Dexie's observability layer, so a live query on the pending count updates. This relies on Dexie 4 internals; `tracking.test.ts` guards each of these facts.
- **2026-09-30 — The middleware is the one piece of sync that is always installed; with sync off it is a pass-through.** `db.use()` only takes effect when the database opens, so installing it on demand would mean closing and reopening the database under live queries. Off, `transaction()` does not widen and `mutate()` returns at its first check. The flag is read in `db.on('ready')` from `syncState` and changed in other tabs by a `BroadcastChannel` message; the feature's `onAppStart` imports the engine only when it is on. Budget: the entry chunk grows by at most 2 KB gzip.
- **2026-09-30 — Tombstones exist only in the outbox and on the server; the server keeps them forever.** A delete leaves an outbox entry whose record is gone at push time, which is sent as `deleted: true`; no local tombstone table is needed because the server only serves winners. A tombstone is about 100 bytes; purging them would let a device that was offline longer than the purge window bring deleted rows back.
- **2026-09-30 — What syncs: 26 tables; never `files`, `snapshots`, `streakDays`, `worldTiles`, `readiness`, `syncOutbox`, `syncState`.** PDFs (up to 50 MB) do not belong in jsonb, and Supabase Storage would add a bucket, policies and a second transfer path to a first version: the resource row syncs and the other device shows the existing "File missing" state, worded "This PDF isn't on this device. PDFs stay on the device they were added on." while sync is on; Storage is an optional 12C. Derived caches are rebuilt from synced history. `planProposals` sync so a proposal can be accepted on either device (applying one already marks the goal's other pending ones stale). `trash` syncs with Blobs replaced by the backup's `{__blob, type, size}` marker; when a remote tombstone removes a local trash row, its real Blobs go back into `files` if a resource still points at them, so a restore on the other device never costs this device the PDF.
- **2026-09-30 — The settings row syncs, minus device paths.** `appearance` (theme, accent and reduced motion; the user's call in 12B1: a phone in dark mode next to a laptop in light mode is common, and the theme is also mirrored per device for the no-flash boot), `notifications`, `blocker.extensionIdOverride`, `blocker.lastSyncedAt`, `blocker.eventsCursor` and `backup.lastRemindedAt` stay on the device; a write that only touches them is not queued (the blocker's 60 s event pull must not push the settings row and overwrite the other device's real change). `onboardedAt` never goes from set to null. `lastCelebratedLevel`, `world.seed`, the two "seeded" flags and `scheduling.lastDailyRunDay` sync on purpose: one level-up moment, one city, no reseeding, one daily roll-forward. `Settings.sync` is removed in v3; the sync config lives in `syncState`, because a synced row cannot hold what is needed before syncing.
- **2026-09-30 — Running and paused sessions are not pushed until they end.** "One running row at a time" stays true on each device, and no device finishes another device's timer or plays its chime. Documented as "a running timer shows on the other device when it ends".
- **2026-09-30 — `xpEvents` is a union by id; awards and reversals get deterministic ids `xp:<key>#<n>`.** Rows are immutable, so LWW on an id only resolves a collision, and deterministic ids turn the same award paid offline on two devices (daily goal, course, streak milestone, a task) into one collision instead of double XP; award, undo, award is the same `#0 #1 #2` sequence everywhere. Existing events keep their uuids. Starter rewards get ids `starter-reward:<i>` for the same reason (the default blocklist already uses `defaultId(domain)`).
- **2026-09-30 — A device's first sync is a merge, never a wipe, and starts with a `pre-sync` snapshot.** It pulls everything first, applies each remote row that is newer than the local row's `updatedAt` (a new device adopts the account's settings), drops local seed rows the account already has (untouched starter rewards and onboarding tasks, duplicate blocklist entries), then queues every local row the server lacks or has older. If the snapshot cannot be written, nothing syncs. A later pull page with 25 or more tombstones (an import, restore or big delete elsewhere) takes another `pre-sync` snapshot first. `SnapshotReason` gains `pre-sync`, kept 5 like the other kinds.
- **2026-09-30 — Import and snapshot restore replace the data on every synced device; Reset erases only this device and turns sync off first.** Import and restore are tracked writes (`clear()` then `bulkPut`), so they propagate, and their dialogs say so when sync is on. A tracked reset would push a tombstone for every row and empty the cloud and the other devices; instead `resetAllData` switches tracking off, clears `syncOutbox` and `syncState`, then clears the data.
- **2026-09-30 — Remote rows raise one `sync.applied` event, not the per-action events.** `task.completed` and friends pay XP and show toasts for things done on this device. `sync.applied { tables, goalIds }` rebuilds streak days (the start-up check), reconciles badges, and heals plan tasks both devices re-planned offline (a goal with two open tasks sharing a `scheduleKey` is re-planned once; `diffPlanTasks` keeps the older, the same one everywhere). Nothing else re-plans on a pull, so two devices cannot ping-pong plans computed at different moments. The apply transaction raises `lastCelebratedLevel` when a page brought XP, so no level-up moment plays for XP earned elsewhere; 12B checks the badge, streak and celebration watchers the same way. The goals feature's daily roll-forward waits up to 8 s for the start-up sync, so the device opened second usually adopts the first one's.
- **2026-09-30 — One tab syncs (Web Locks leader); triggers are start, focus, `online`, 5 minutes, 3 s after a write, Sync now, and a keepalive flush when the page is hidden.** Supabase rotates refresh tokens, so two tabs refreshing at once could sign each other out. Other tabs keep tracking writes and ask the leader to sync over a `BroadcastChannel`; every tab reads status from `syncState` and the outbox count through live queries. Pages of 500 rows, one transaction each, with the main thread handed back between pages; a steady cycle stays under 30 ms of main-thread work.
- **2026-09-30 — Sign-in is a magic link (PKCE) or the code from the same email.** On iOS an installed PWA has its own storage and a link from Mail opens in Safari, which has neither the PKCE verifier nor the data, so the link alone could never sign the phone app in. The README asks the person to add `{{ .Token }}` to the Magic Link and Confirm signup email templates, to allow-list `/settings/sync` on the Netlify origin and localhost, and to turn off new sign-ups after the first sign-in. The Settings copy warns that Supabase's built-in email sender allows only a few emails an hour.
- **2026-09-30 — Every server row carries its `schema_version`.** An older row is migrated on read with the backup migrators; a newer one stops sync before that page is applied ("Another device runs a newer Forge. Reload to update this one") without moving the cursor. Dexie table names are now part of the sync format: never rename a table.
- **2026-09-30 — 12B1 as built: the middleware chains on Dexie promises, never on native `await`.** Dexie's hooks middleware (level 2) and cache middleware (level 0) read the current transaction from Dexie's zone (`PSD.trans`) when `mutate` is called. A native `await` inside a middleware loses that zone, so the first build crashed the hooks middleware on every tracked write. `.then` on the promises DBCore returns (Dexie promises) keeps it, which a scratch test confirmed. Reads that must happen before the write (old settings for the device-path comparison, existence for append-only tables, the keys of `clear()`) are issued before the mutation in the same transaction, and IndexedDB runs them in order. `tracking.test.ts` covers every write path with timestamp hooks installed, so a regression shows at once. The middleware stays at level 10.
- **2026-09-30 — 12B1 as built: details.**
  - One `SyncTracker` per `ForgeDB` (`db.syncTracker`: flag, stamp floor, write listeners), loaded by a sticky `on('ready')` on every open, so migration and unit tests that open several databases stay independent. Only the app's singleton listens on the `forge:sync` BroadcastChannel, and only in a browser.
  - A key whose operation failed inside a bulk write is not queued.
  - `upgradeV3` filters before it modifies, so running it again writes nothing (a `modify` that changes nothing still wrote and was stamped).
  - `resetAllData` both switches tracking off (and broadcasts it) and marks its transaction untracked, so a tab that has not heard the broadcast yet cannot queue tombstones either. It also clears `syncOutbox` and `syncState`.
  - `BACKUP_TABLES` leaves out `snapshots`, `syncOutbox` and `syncState`, and `ignoredTables` lists all three, so an old file with them imports without a warning.
  - `TABLE_LABELS` names the two new tables. The snapshot kind label for `pre-sync` is "Before sync".
  - Budgets with tracking on: a re-plan with nothing new queues nothing and stays under 300 ms; a completion stays under 100 ms and queues the task and `xp:task:<id>#0`.
  - Measured with `npm run build` (gzip -9 of every JS file `index.html` loads): 359,866 → 361,318 B, **+1,452 B**. The middleware sits in the shared `db` chunk (+1,690 B); `index-*.js` is 63 B smaller (121.10 → 121.07 kB in Vite's report).
  - The flaky `onboarding.spec.ts` case "someone with data who never onboarded" (1 in 6 before this change, 3 in 6 after, from start-up timing) wrote the settings row while the app was open, and the app could mark onboarding done before the test's check. It now uses `putRowsWhileClosed`, as the daily-goal spec does: 8 of 8.

- **2026-09-30 — The crash export and every backup leave the sync bookkeeping out.** `buildBackup` writes `syncState` and `syncOutbox` as empty lists whatever it is given, and the crash screen's raw dump does not read those tables at all, so no file can carry the session's tokens. `exportData.test.ts` puts a session in `syncState` and checks no token reaches the dump.
- **2026-09-30 — Features never import `@/db/sync/*`.** ESLint bans it; features reach sync through `@/db/repos/sync`, `@/db/repos/syncGate` and `@/db/hooks/useSyncState` only.
- **2026-09-30 — The pure request building lives in `logic/syncRequests.ts`**, not `logic/sync.ts` as §4.7.9 said: 12B2 and 12B4 were built at the same time and one file per owner avoided a clash.
- **2026-09-30 — Text is scrubbed before a push.** A lone UTF-16 surrogate (a string cut through an emoji) or a NUL makes Postgres refuse the jsonb and would wedge the whole batch; they become U+FFFD / are dropped on the way out. The pulled-back copy then differs from the device's by those characters, which the engine treats as its own echo (same stamp, same device), not a conflict. The engine still skips and reports a row whose batch keeps failing with 400, so a different server refusal cannot wedge sync.
- **2026-09-30 — "Project paused" is shown only after repeated 5xx/540 answers,** as §4.7.7 says; one 540 can be a blip.

After each push the engine (12B3) raises `maxSeenStamp` to the largest pushed stamp, so a clock stepped back after a reload cannot give an edit a stamp older than one this device already pushed.
- **2026-09-30 — Test fixtures never contain a secret-shaped literal.** GitHub push protection refused a fake `sb_secret_…` key in a test; such keys are assembled at runtime (`['sb', 'secret', …].join('_')`).


## Cloud sync (Phase 12B3: the repo engine)

- **2026-09-30 — `runSyncCycle(server, opts)` never throws and is the only way a cycle runs.** It returns `off` (no row, not enabled, or switched off mid-cycle), `busy` (one cycle at a time per page), `ok` (`mode`, `pushed`, `pulled`, `applied`, `refused`) or `error` (`error`, `retryAfterMs`, `httpStatus`, and `cause` for a database error that is not a transport failure), and writes `lastAttemptAt`, `lastSyncAt`, `lastError` and `clockSkewMs` to `syncState`. The engine (12B5) only schedules cycles and hands the error to `planRetry`. The same file exports the lifecycle the UI needs, because features may reach sync only through `@/db/repos/sync`: `getSyncState`, `getSyncSession`, `saveSyncConfig`, `savePendingLogin`, `startSync(session)`, `saveSession`, `markSignedOut`, `stopSync`, `pendingChangeCount`, `pendingPushRows` (the page-hide flush).
- **2026-09-30 — Every write to `syncState`, and every apply, checks that the row still belongs to the cycle (`enabled` and the same `deviceId`).** Signing out or resetting during a request throws `CycleCancelled` inside the transaction (it rolls back) and the cycle returns `off`, so a slow cycle can never bring the state, or a page of rows, back after the person turned sync off.
- **2026-09-30 — `SyncStateRow.preSyncFor` (optional, the `deviceId` a `pre-sync` snapshot was taken for) is the one edit to `db/types.ts`.** A first sync that restarts must not snapshot again: the data is half merged by then and the keep-5 pruning would eventually push out the snapshot of the real "before". `syncState` is never synced or backed up, so no migration; `defaultSyncState()` leaves it absent, so sign-out clears it.
- **2026-09-30 — A push that keeps failing with a content refusal is bisected, and the record at fault is held, then dropped only once the server has taken other rows (review fix).** Halving applies to 413 and to any 4xx that is not 401, 403, 408 or 429 (`isRowRejection`). A record left alone and refused keeps its outbox entry: one refusal cannot tell a bad record from a bad request (a setup SQL without a column answers every push with `PGRST204`, a proxy answers 400). It is only skipped when the next 200 entries are read, so the queue still moves on. At the end of the push (`finishHolds`): if the server took at least one other row in the cycle and there are at most 10 held records, they are removed with compare-and-delete and named in `lastError` (`“Title” … stays on this device. Everything else synced.`), and the cycle succeeds; otherwise **nothing is removed**, the cycle still pulls, and then fails with the server's own error so the retry schedule and the person see it. A record refused and then edited during the cycle is pushed again at once (its new stamp is not held). A lone refused row is therefore kept, and goes out as soon as any other change is accepted. A record over 8 MB (`batchRows`) is different: it is never sent whatever the server says, so its entry is removed at once and it does not count toward the 10.
- **2026-09-30 — A 401 refreshes the session once per cycle and repeats the call; a lost answer to the refresh is tried once more at once.** The `refresh` option is how the engine plugs in `auth.refreshSession` (db cannot import features) and must make its `SyncServer` use the new session. An offline or server error from the first refresh is retried once (Supabase's reuse window lets the same token through); `refresh_token_already_used` or any refusal then ends the cycle as `signedOut`: the tokens are dropped, the message is always "Sign in again to keep syncing. Your changes are kept on this device.", tracking stays on. A token within 60 s of expiry is refreshed before the cycle starts.
- **2026-09-30 — A page is applied in one transaction over only the tables it touches, plus `syncOutbox`, `syncState`, and `settings`/`xpEvents` (the level) or `resources`/`files` (trash) when needed.** Smaller than "every synced table" so a page blocks fewer writers. Inside it: `decideApply` per row with the local row and outbox entry read in the same transaction; identical rows are not rewritten; the settings row merges with `mergeRemoteSettings` and is never deleted by a tombstone; a pulled trash row keeps the real PDF bytes this device already holds (`keepLocalTrashBlobs`); trash tombstones run after the puts of the same page so a restored resource is already there when the bytes are rescued into `files` (`trashFilesToRescue`); the cursor and `maxSeenStamp` advance with the data. `observeRemoteStamp(pageMax)` is called after the commit, only when the page raised the maximum (`advancePull` already applied `stampCeiling`).
- **2026-09-30 — XP that arrives by sync never plays a level-up: the apply transaction raises `settings.lastCelebratedLevel` to the level the local XP log now reaches (untracked), when the page brought `xpEvents` or settings.** The level watcher compares two live queries that refresh separately, and `claimLevelCelebration` re-reads the row in a transaction, so even a render that sees the new XP before the new level finds nothing to claim. No per-action event (`xp.changed`, `task.completed`) is emitted for remote rows, so no XP is paid, no toast shown, no animation run. `gamification/handlers.ts` needed no change for this.
- **2026-09-30 — The start-up gate is a flag and a timer, in the entry chunk, and nothing awaits it in the start-up chain (review fix).** `waitForStartupSync(8000)` resolves at once when `db.syncTracker.enabled` is false (no I/O), else when the first cycle of the page load ends, however it ends (`runSyncCycle` settles it in a `finally`; the engine calls `settleStartupSync()` if it decides not to run), or after 8 s. Goals' `onAppStart` schedules `await waitForStartupSync(8000)` then `runDailyPlanning` and returns at once (errors go to `recordError`), like the safety chores: `runAppStart` runs features one after another in folder order, `goals` sorts before `sync`, so a hook that awaited the gate would keep the sync feature from starting its engine until the wait timed out (the gate would always run its full 8 s, roll-forward would run before the first sync, and every feature after goals would start 8 s late). 12B5 must still start the first cycle promptly after first paint, and call `settleStartupSync()` itself when it runs none.
- **2026-09-30 — `sync.applied` handlers: progress rebuilds `streakDays` with the full start-up check (quiet, no milestone XP), badges reconcile without announcing, goals heal duplicate plan tasks.** `healDuplicatePlanTasks` (`db/repos/syncHeal.ts`, loaded on demand from the goals handler) re-plans a goal once with the new `RebalanceReason` `'sync'` when it has two open tasks for one plan item (finished tasks do not count: the same chunk finished on two devices is two real sessions). The event carries only tables that changed and the goals whose plan tasks arrived. `worldTiles` and `readiness` need nothing: the world is built from live queries and never stored.
- **2026-09-30 — The server's clock is read at most once an hour, remembered in memory per device id.** `serverTime()` runs at the start of a cycle when it was never measured, or the last measurement is an hour old, or this page's clock went backwards; the skew is stored in `syncState.clockSkewMs` and, added to this device's time, sets the ceiling for the remote stamps the hybrid clock takes (`stampCeiling`).
- **2026-09-30 — Tests simulate devices by saving and loading the whole database, not by opening several.** Repos use the `db` singleton, so `src/test/devices.ts` swaps every table (outbox and `syncState` included) in one remote-apply transaction, and gives each device its own `StampClock` (installed under `db.syncTracker` with `Reflect.set`, test-only) and wall clock (real time plus an offset), because the tracker's clock function is `Date.now` captured at construction and fake timers cannot move it. `src/test/fakeSyncServer.ts` is the real `SyncServer` over `SyncServerModel` with offline, `failNext`, lost answer, 413, refused row and clock-offset switches; its clock advances at least 1 ms per call.
- **2026-09-30 — On a first sync the account wins over a seed row with a fixed id (review fix).** `starter-reward:N` and `default:<domain>` are the same id on every device and a new device seeds them with `updatedAt = now`, so they are not seed duplicates (same id) and the bootstrap stamp comparison would let them beat anything the owner did on the account's side: editing a starter reward, archiving or deleting one, removing a default site would all be undone by adding a second device. While applying a first-sync page, a local row that is untouched (`accountWinsOverSeed`: a starter reward with `updatedAt === createdAt`; a default site that is a plain block entry, on, without pattern or note, `updatedAt` within 10 ms of `createdAt`, the seed spreads `createdAt` by 1 ms per site) is replaced by the account's row whatever the stamps say, live or deleted (a tombstone deletes it here without one of our own), and its queued change is dropped. A seed row the person already changed on this device stays an ordinary row. Applies only while bootstrapping; restoring the default sites looks like a seed and yields the same way, which is the lesser evil.
- **2026-09-30 — Measured (12B3).** Entry `index-*.js` + every modulepreload of `dist/index.html`, gzip -9: 314,374 B without the three always-loaded handler edits, 314,707 B with them, **+333 B** (goals gate and heal handler, the streak and badge `sync.applied` handlers, `syncGate.ts`). `db/repos/sync.ts`, `syncApply.ts` and `syncHeal.ts` are in no entry chunk. Budgets (CPU, fake-indexeddb, median of runs): a steady cycle with 50 changed rows 12–22 ms (plan: 30 ms in Chrome), applying a 500-row page 80–107 ms (plan: 60 ms in Chrome); the tests allow 100 ms and 400 ms.


## Cloud sync (Phase 12B5: engine and Settings)

- **2026-09-30 — The engine is a scheduler (`engine.ts`, class `Scheduler`) that knows nothing about cycles, plus one `createEngine(platform)` that is given the browser.** A cycle runs: once after the browser is idle at start (400 ms, 1 s for the tab that turns sync on, so other tabs hear the tracking broadcast first), 3 s after a queued write (more writes push it back, never past 30 s from the first), when the tab becomes visible or the window is focused and the last cycle ended over 30 s ago (in the tab that syncs; another tab asks it, see below), on `online`, every 5 minutes while visible, and on "Sync now" (which also forgets the backoff). A trigger during a cycle sets `again`: one more cycle runs after it. After a failure `planRetry` decides (15 s, 1, 5, 15 min ±20 %; a 429 at least as long as it asked; offline waits for `online`, with the backoff as a fallback; signed out, setup, forbidden and update-needed stop until the person acts; a 413 that the repo engine could not split is an ordinary backoff). A write, a focus or the 5-minute tick never jumps a pending backoff. Everything runs under fake timers in `engine.test.ts` (Scheduler: 40 cases; engine, leader and flush: 20 more).
- **2026-09-30 — "Project paused" needs three consecutive cycles whose last transport error was `suggestsPaused` (5xx of 520 and up).** The engine wraps the `SyncServer` it gives `runSyncCycle` to keep the last `SupabaseError`, because the cycle's result only carries the status. One ordinary failure in between, a success or "Sync now" starts the count over.
- **2026-09-30 — One tab syncs: a Web Lock `forge:sync` held for the tab's lifetime, asked for without waiting first.** `ifAvailable` tells a tab that will not lead at once, so it opens the start-up gate (`settleStartupSync`) immediately instead of making goals wait 8 s for a cycle that never comes; it then queues, and takes over when the leader closes. Without Web Locks every tab runs. The tabs share `BroadcastChannel('forge:sync')` with the tracking middleware (which ignores these messages): `sync-now` (a follower asks), `wrote` (a follower queued a write: the leader starts its write timer), `nudge` (a follower's page was focused or became visible: the leader syncs if its last cycle is over 30 s old, because its own 5-minute rhythm pauses while it is hidden), `engine?` and `engine` (the leader's running flag, retry time, paused flag and first-sync progress, so every tab's status line agrees). A "Sync now" pressed before the election has answered is held and applied when it has. **Only the leader runs cycles, whatever the page does (review fix):** `visible`, `focus` and `online` used to reach the scheduler in every tab, so switching to a follower ran a full cycle there (a second token refresh, a second bootstrap, pull pages applied in two transactions). Now a follower does nothing on `online` (the leader's page hears it too) and posts `nudge` on `visible` and `focus`, and says nothing before the election has answered. Checked in a real browser with two tabs: the follower made no request when its page was focused, shown or back online.
- **2026-09-30 — The hide-time flush runs in any tab, not only the leader.** It is push-only, idempotent (the same stamp from the same device is accepted) and never refreshes a token, so it cannot cause the rotation problem the lock exists for, and a follower hidden right after an edit still sends it. It needs pending rows that fit in 60 KB (`fitsKeepalive`) and a token good for another minute, and it leaves the outbox alone: the next cycle pushes the same rows again.
- **2026-09-30 — The always-loaded part is `feature.ts` (manifest), `index.ts` and `queries.ts` (two reads of `db.syncTracker`).** `onAppStart` imports the engine at once when the in-memory tracking flag is on, and in every case registers one watcher for tracked writes that is never removed (review fix: it used to be registered only when sync was off at boot, so a tab whose engine had stopped, because a cycle found sync switched off in another tab, never got one again). A tracked write is a reason to have an engine in this tab: another tab turning sync on makes this tab's writes tracked and its first write starts an engine (a follower if another tab leads), and after sign-out and sign-in elsewhere the next write starts a new one; while an engine runs, `startEngine` returns it. ## Cloud sync (review fixes, 2026-09-30)

- **2026-09-30 — The first sync always takes its `pre-sync` snapshot, even of a nearly empty device.** `skipIfEmpty` counted only tasks, goals, sessions and the like, so a device holding only courses, rewards, a blocklist, settings or XP took none, and `preSyncFor` then stopped it from ever trying again. An empty snapshot is a few KB.
- **2026-09-30 — The oldest `pre-sync` snapshot is never pruned** (retention keeps the newest 5 and the oldest). Safety snapshots before big pulls and re-enables are also `pre-sync` and would have rotated out the data as it was before sync first touched it. Chosen over a new `SnapshotReason`: no type, label, or snapshot-format change, and an older build still prunes by its own rule. A person who deletes that snapshot by hand makes the next oldest the pinned one.
- **2026-09-30 — The safety snapshot counts deletions over the whole cycle, not per page.** An import elsewhere whose 1,000 tombstones are interleaved with puts can stay under 25 per 500-row page; the cycle now snapshots before the page that brings its total here to 25. `needsSafetySnapshot` (per page) is gone. A restarted first sync (snapshot already taken for this `deviceId`) no longer marks the cycle as snapshotted, so the check stays armed for it.
- **2026-09-30 — Signing in to another account clears the outbox** (in the same transaction as the new `deviceId`). Pending puts and tombstones were queued for the first account, and a tombstone pushed into the second could delete its row under the same id (fixed-id seeds share ids everywhere). The first sync re-queues every local row by its stamp. `maxSeenStamp` stays: it only keeps new stamps above the ones the local rows already carry.
- **2026-09-30 — A seed-duplicate blocklist entry is dropped only while untouched**, the same test as `accountWinsOverSeed` (`updatedAt` within the seed's spread of `createdAt`). One the person switched off or edited here is pushed; a visible duplicate beats a lost edit.
- **2026-09-30 — A Trash tombstone keeps the PDF bytes whether or not a resource points at them yet; nobody's bytes are removed 30 days later.** A restore elsewhere puts the resource before it deletes the trash row, but that put can come later (edited after the restore, held by the server), and this may be the only device with the bytes. `trashFilesToRescue` returns every real Blob unless the row is past its `expiresAt` (a purge). A kept file is written with `updatedAt` = now; stored files are never edited, so `updatedAt > createdAt` marks one without a type change. Each cycle, `rescuedFilesToDrop` removes kept files no resource (live or in a Trash entry) points at after 30 days, the Trash's own window: after "Delete forever" elsewhere the bytes stay here that long. The apply no longer reads `resources` for a trash page.
- **2026-09-30 — Only a 4xx with a PostgreSQL row code is a row refusal** (class 21 cardinality, 22 data, 23 constraint, 54 limit). A bare 400/404/409/422 from a proxy or a schema-cache reload used to be bisected down to "bad rows", up to 10 of which were then dropped for good once the server took other rows. Without such a code the cycle now fails and everything stays queued.
- **2026-09-30 — A sign-in link the server refused forgets its PKCE verifier** (`codeVerifier: ''`, email and time kept so the code field stays on screen); offline, 5xx, 408 and 429 keep it for a retry. Opening a link again then says it expired, without a request. Not cleared outright: the code from the same email must stay typeable, which the Waiting step needs `pendingLogin` for. No time-based expiry: Supabase's link lifetime is configurable up to a day.
- **2026-09-30 — No JWT-shaped literals in tests.** The anon JWTs in the Supabase client and request tests are joined from their three parts at run time, like the fake `sb_secret_…` keys.
